# @keelwerk/transport-trpc

The tRPC projection of the action surface at `/trpc` (section 16.7): the router built at `listen` for every API version, `TrpcRouterOf<App>` as a type fragment of the generated file, subscriptions over server-sent events or a WebSocket with the stream token as the event id, and the shared conformance suite.

- Module: list `trpc` in `modules`, or `trpcTransport({ path, transformer })` for static options; per-backend `config` holds `cors`, `maxBodyBytes` and `websocket` (default `false`). A request body of more than `maxBodyBytes` bytes is refused with status 413, tRPC's `PAYLOAD_TOO_LARGE` and `core.payload_too_large`, as the other transports refuse it. The host reads every body within its own `maxBodyBytes` first, so only a setting below the host's takes effect; at or above it (the defaults are equal) the host answers a larger body 413 in its own wire form before the mount runs.
- Static options: `path` (default `/trpc`) and `transformer` (`'superjson'` by default, `'json'` for the plain wire of section 16.4.2 and `TrpcRouterOf<App, false>`).
- Client: pass `keelwerkSuperjson()` as the `transformer` of every link (unless the app sets `transformer: 'json'`), send the command id as `Idempotency-Key` and `Prefer: respond-async` as the header of the call, and read subscriptions with `httpSubscriptionLink`.
- Batching: a request of several calls (`batch=1`) with `Idempotency-Key` or `Prefer: respond-async` is refused, so send such a call alone. A JSON-lines batch (`trpc-accept: application/jsonl`, tRPC's `httpBatchStreamLink`) that calls a command or a cookie-hinted action is answered whole, after every call has run, so that its `Set-Cookie`, `Keelwerk-Command-Id`, `Keelwerk-Effects` and `Preference-Applied` headers reach the caller; a slow query in such a batch delays every answer of that batch. To keep queries incremental, send such calls alone or through a link that does not stream. Every other JSON-lines batch streams incrementally.
- Subscriptions: every message holds exactly one frame, an item (`{ data }`, and `id` for an item that carries a state token) or a control frame (`{ control: 'head' | 'reset' | 'gap', ... }`, never with `data`), and never the bare event, so an event of any shape, even one with a member named `control`, is an item. A frame that carries a state token (an item of a resumable action, `head`, a `reset` with a state) is tracked: `httpSubscriptionLink` hands it over as `{ id, data: <frame> }` and resumes from that `id`; the other frames arrive as they are. An event with no value (the `void` output of an empty shape) arrives as `undefined`, or as `null` with `transformer: 'json'`, so that the item keeps its `data` (the router type says so: with `TrpcRouterOf<App, false>` a `void` event is typed `null` and a `string | undefined` event `string | null`). Unwrap a value that has a string `id` once, then narrow with `'data' in frame`:

  ```ts
  onData(value) {
    const frame = 'id' in value ? value.data : value; // tRPC's tracked wrapper
    if ('data' in frame) show(frame.data); // an item: the event
    else if (frame.control === 'reset') resubscribe(); // head, reset, gap
  }
  ```

- WebSocket: a backend turns it on with `websocket: true` in its `trpc` configuration (default off); the endpoint is the mount path (`/trpc`) with the subprotocol `keelwerk.trpc.v1`, and a backend without it answers the upgrade 404. A client is tRPC's `createWSClient({ url, WebSocket: trpcWebSocket(WebSocket), connectionParams })` with `wsLink`: `trpcWebSocket` offers the subprotocol, which tRPC's client does not. Only queries and subscriptions run over the socket: a command (it needs its command id, `Prefer` and effects headers, and it is the call that writes a decision record, which core builds only for commands and reactions, so a call over the socket never writes one) and an action with a cookie hint (it needs `Set-Cookie`) are refused `core.unsupported`, so send them over HTTP, and a call that starts after the mount began to close is refused `core.unavailable` (retry after 1 second), as HTTP refuses it. A subscription that is already open on a socket is not ended by the mount's close. The credentials are the four members of `connectionParams` (`token`, `tenant`, `backend`, `apiVersion`), sent once as tRPC's first message when the URL has `connectionParams=1`, and never in the URL; without them the session of the upgrade (its cookie or header) is kept. The host holds the socket's protections (origin check, session check, subscription slots, maximum duration, ping), and every query and subscription meets the session check before it runs. The frames are the ones of server-sent events: a tracked frame arrives as `result.id` and `result.data = { id, data: <frame> }`, so unwrap a value with a string `id` once, then narrow with `'data' in frame`. At most 20 calls go in one message (a client that resubscribes more than 20 subscriptions in one message after a reconnect gets the surplus refused per id), and the socket sends no deprecation notice. A message of more than the backend's `maxBodyBytes` bytes (counted in bytes, as a body is) is dropped and closes the socket 4400 `core.payload_too_large` (only a setting below the host's `liveSocket.maxMessageBytes` takes effect; at or above it, as with the defaults, the host closes a larger message 1009 before the mount reads it); a socket that sends more than four times the smaller of that and the host's `liveSocket.maxMessageBytes` before its first message is handled closes 4429 `core.quota_exceeded`; a malformed first message closes it 4000 `protocol_error`, and no first message in time 4000 `hello_timeout`. Credentials of the first message that the host refuses, a token that resolves to nobody or a principal that has expired, close the socket 4401 with `core.unauthenticated` as the reason, the code HTTP answers 401 with; credentials of the upgrade request itself that the host refuses (an expired cookie or header principal) are answered 401 before the handshake; a stream ticket in the URL authenticates nothing and is spent. Any other refusal of the first message closes the socket with the close code of its kind and the error code as the reason (for example 4400 `core.api_version_unknown`, 4403 `core.csrf`, 4404 `core.api_version_retired`, 4429 `core.quota_exceeded`). A page may open the socket with the user's cookie only from the tenant's own domains or an origin listed in the backend's `trpc.cors` (a cookie upgrade whose `Origin` is not allowed, or that has neither an `Origin` nor `Sec-Fetch-Site: same-origin`, is refused 403 `core.csrf`), so list in `cors` only origins you trust with the user's session. Behind a reverse proxy, set the host's `trustedProxies`: without it every client counts as the proxy's address, and all of them share the anonymous bound per address (`live.maxStreamsPerPrincipal`, default 20), which every socket that sends its credentials in `connectionParams` meets until its first message. The other bounds are the host's `liveSocket` options: `helloTimeoutMs` (10 s), `heartbeatMs` and `pongTimeoutMs` (30 s, 10 s), `revalidateMs` (60 s), `maxSubscriptionsPerSocket` (100), `maxMessagesPerWindow` per `messageWindowMs` (200 per 10 s; more closes 4429 `rate_limited`), and `live.maxDurationMs` (24 h, then 1000 `max_duration`). The queries running at once on one socket are bounded by the host's `liveSocket.maxPendingInvokes` (default 32, the same bound as `keelwerk.live.v1`): a query past it is refused `core.quota_exceeded` unrun.
- Known limits: a browser client on another origin needs CORS headers for `trpc-accept` and `preference-applied` that the host does not list yet; `hints.trpc.expose: false` hides a procedure at run time but `TrpcRouterOf` still lists it; a stream of this transport is not ended when its session ends, its key is revoked or the host stops, until the host fixes the life of a mounted stream once; this holds for server-sent events and JSON lines only, since the host ends a socket itself (4401 when its session ends, 1001 at stop, 1000 `max_duration`).
