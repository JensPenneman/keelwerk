# @keelwerk/module-api-keys

API keys: a person creates keys that act as them, and the key resolver turns a presented key into the principal of its owner. It builds on `@keelwerk/module-accounts` (optional at run time), imports nothing from `@keelwerk/module-auth`, and takes its token format from the core's key service.

- `api-keys.key` (state, data subject `subject`, indexed): `publicId`, `verifier` (hidden, HMAC under the tenant key), `label` (free text the owner writes, personal), `scopes`, `expiresAt`, an optional `apiVersion` pin, `lastUsedAt`, `revokedAt`. An erasure of the owner reaches the key rows, so the key stops resolving: `resolve` finds no row (the one refusal) and `fromRef` answers nothing.
- `api-keys.create`: for a signed-in person only; a principal that came from a key cannot create a key, because a leaked key must not mint keys that outlive its own revocation. It issues `kwk_<public id>_<secret>` once (`shownOnce`, never stored, logged or put into a receipt, event or job); the row keeps the public id and the verifier. A key holds `read` or `write`, may name `transport:<id>` scopes, and may expire. A person holds at most 100 unrevoked keys (expired ones count); the next `create` is a conflict until one is revoked, so a person cannot make their own deactivation heavy.
- `api-keys.key.revoke`: the owner revokes a key, once; an operator of the tenant may revoke any key too (rule `api-keys.key.operator`), and reads none: module-auth gives an operator no read of a person's credentials and sessions, so this rule names `revoke` only. A key is also reached through the deactivation of its owner. `api-keys.key.query` and `get` are the generated reads: an owner sees their own keys, never a verifier.
- Scopes: `read` reads in every module; `write` also runs commands; `transport:<id>` binds the key to those transports, and on any other transport it is refused like an unknown key, and a stream ticket it issued is not redeemed on another transport either. The read scope covers queries and subscriptions in every module and no command, `live.ticket` included: a program opens a stream with its key in the `Authorization` header (server-sent events) or in the socket's upgrade or hello, and a stream ticket exists for a browser's `EventSource`, which cannot send headers. The rule `api-keys.readOnlyKey` is a deny rule over the selector `{ kinds: ['command'] }` (G13), so a key without `write` runs no command in any module, with the reason "This API key has the read scope only."
- The resolver (`api-keys.key`, a principal resolver of the core): a well-formed `kwk` token costs one load and one verification whether the key exists, is revoked, is expired or belongs to another tenant, and answers one refusal. Keys are looked up in the tenant the carrier names. `fromRef` re-resolves the stored reference when queued work runs, and the live hub revalidates an open stream through the same resolver, so a revoked or expired key stops there.
- Queued work and a transport-bound key: `fromRef` judges a key that names transports under the transport the work was accepted on, which is the carrier's for a redeemed ticket and for the revalidation of a stream, and the one its accepted receipt records for a job. So an asynchronous command a transport-bound key started on a transport it names runs, while work that key queued through an `enqueue` effect or a deferred `invoke`, and a job whose receipt is gone, fail `unauthenticated` ("The principal of this job no longer resolves."); a key that names no transport is not judged by it. A later mail submission must queue its follow-up work as an asynchronous command with a receipt, or under the module's service principal.
- Revoking a key and the work it started: queued work stored under the key's reference (asynchronous commands, enqueue effects) ends at its next re-resolution. Timers, reactions and effect continuations that a key's commands caused run as the module's system principal and complete after the revocation, by design (docs/architecture.md, about line 3407): a decision already accepted still completes. Whoever handles a leak should know that both exist.
- Deactivating the owner: with accounts selected, the reaction to `accounts.profile.deactivated` runs `api-keys.revokeSubject` as the module's system principal and revokes every live key of the profile in the deactivating unit, as module-auth does for credentials and sessions. The command pages through the keys by id, a thousand at a time, until a page comes back short, so no number of keys can hold the deactivation back or leave a live one behind.
- Last use: at most once an hour, through the keyed timer `api-keys.lastUse:<key id>`, whose input is the key id and nothing else. `api-keys.recordUse` and `api-keys.repinKey` run as the module's own service principal, so they work for a read-only key, and no caller can invoke them from outside.
- API-version pin: a key pinned to a retired version is served at the version `retiredPinTarget` names (the check `repinRetiredPins` uses) at once, and the keyed timer `api-keys.repin:<key id>` moves the stored pin.
- A lookup costs the same key-store work whether the presented key exists, is revoked, is expired, belongs to another tenant or is unknown: the resolver verifies an unknown key against the core's `absentVerifier`, and the kernel then spends the work of opening a stored one.

Not here: app passwords for mail listeners (`transport:imap`, `transport:smtp-submission` scopes are stored, but no rule grants a listener access: a rule cannot see the transport).

`src/module.generated.ts` is produced by `pnpm manifests` and the files under `migrations/own/` by the CLI migrations producer; neither is edited by hand.
