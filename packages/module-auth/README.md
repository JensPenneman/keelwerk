# @keelwerk/module-auth

Credentials and sessions: sign-up, login, logout, revocation and the session resolver. It builds on `@keelwerk/module-accounts` (optional at run time) and works without it.

- `auth.credential` (chain, data subject `subject`): a password credential per person, `identifier` (the e-mail address, personal, unique among active password credentials), `verifier` (an Argon2id PHC hash, hidden and sealed in events), `lastUsedAt`, `revokedAt`; domain events `revoked` and `signedUp`.
- `auth.session` (state, data subject `subject`): `publicId`, `tokenVerifier`, the authentication and expiry instants, client metadata (`userAgent`, `address`, personal and sealed).
- `auth.signUp`: public and rate-limited; creates a password credential under a fresh opaque subject. A taken identifier is `auth.identifier_taken`.
- `auth.login`: public and rate-limited; verifies against a dummy hash for an unknown identifier, rehashes with the current parameters when needed, issues `pss_<public id>_<secret>` once (`shownOnce`, never in the receipt). The `http.cookie` hint sets `__Host-keelwerk_session` for browser requests; the `cli.login` hint names `sessionToken`.
- `auth.logout`, `auth.session.revoke`, `auth.credential.revoke`, `auth.revokeSubject` (internal; invoked by auth's own reaction to a deactivation) and `auth.revokeSessions` (internal; the job `revokeSubject` sets as a keyed timer, which sets itself again until the last page), `auth.whoami`.
- The session resolver (a principal resolver of the core): cookie or bearer token; a stale cookie is anonymous and clears the cookie, a stale bearer token is `unauthenticated`. When a session was last extended more than five minutes ago it sets a timer for `auth.extendSession`, keyed by session; the job runs as the module's own service principal with the session in its input and judges the session itself, so a session that was revoked or expired, or whose credential was revoked, before the job ran is no failed job (it decides nothing). The job moves the idle expiry from the instant of the request that queued it (`seenAt`), never from the time the job runs and never backwards; a job with no `seenAt`, as a 0.1.0 deployment left them (they run as the user of the session), decides nothing. For a cookie request the answer also carries a renewed cookie with the new expiry, which the host sets on a browser response under host-based tenant resolution; a bearer token never becomes a cookie.
- The rate-limit rule (`invocationMiddleware`): `addressAttemptsPerMinute` (10) per remote address charged at admission, `identifierFailedAttempts` (5) per `identifierFailureWindowMinutes` (15) per identifier charged on a declared failure. An IPv4 address is its own bucket and an IPv6 address counts by its /64 prefix (a mapped one as the IPv4 address). Beside them, a step that writes the credential after it proved the password (a login, and the rotation of a password change) is refused with `core.rate_limited` once the credential holds `successfulLoginsPerMinute` (6) sessions authenticated in the last minute, and appends nothing; a login, the new session of a password change and a reauthentication of a session each count one (it sets `authenticatedAt` to now); a wrong password never counts, and is answered as a wrong password whatever the count. A carrier without a connection (an in-process call of `auth.login` or `auth.signUp`, or a transport that builds its own carrier) is charged one shared bucket for an unknown address, the same key the stream limits use, so having no address never goes past the address limit; the operator socket reports the address `unix`, one shared bucket; `host.fetch` always has an address: its caller names the address (`HostFetchOptions.remoteAddress`), else the loopback, so calls that name none share one bucket. Tests that go through the host give each request its own address with `clientFetchOf` or `TestRuntime.fetch`, or name one, instead of raising `addressAttemptsPerMinute`.
- The erasure of a person asks the module, through the core's extension point `erasureReach` (`addressesOf`), for the identifiers of the credentials under that subject (revoked ones too), and which of the addresses asked about a live credential of another subject holds now (`heldByOthers`: that is the other person's address, and the kernel drops it for every module), right before the person's keys are destroyed, so that `members` can find the pending invitations to those addresses (section 14.7.5 of the architecture document). The answer is read only while the key opens; nothing is written.

A login appends one `loggedIn` event to the credential (`auth.credential.loggedIn`, payload `{ at }`; a rehash adds the update of the verifier before it), and when accounts is present the reaction `recordLogin` writes the instant to the profile's `lastLoginAt` in a job, after the login committed. The credential carries the event because the session is a `history: 'state'` entity, whose records are transient and reach inline reactions only; a compose check refuses an asynchronous reaction on such an entity. The job writes only when the profile has no login time yet or an earlier one, with the version of the row it loaded, so jobs that run out of order leave the newer time. An app that composes auth with accounts needs an event worker that runs `asyncReactions` (`consumers({ consumers: [reactionDispatcher()], runs: ['asyncReactions'] })` of `@keelwerk/events`); without one the boot is refused for `auth.recordLogin`. A password change, a reset and a re-authentication record no login.

Deactivating a profile writes the profile and nothing else of the person: auth's reaction enqueues the job `auth.revokeSubject` (an internal, asynchronous command run as the module's own service principal), which revokes the credentials and sets a keyed timer, `revokeSessions:<subject>`, whose job (`auth.revokeSessions`) revokes the sessions a page at a time. No write of the person to a credential or a session can make the deactivation fail. From the commit of the deactivation the person's principals are refused by the enricher of accounts, and their open streams end there; the rows are marked revoked when the jobs have run, so a runtime without job workers never marks them. A login made between the deactivation and the job opens a session that never resolves.

`auth.requestPasswordReset` stores and delivers nothing itself: it sets one keyed timer, for the credential it found or for a decoy id, and the job `auth.deliverPasswordReset` (an internal command of the module's own service principal) issues the token and hands it to the reset delivery fillers. Both answers take the same steps; the delivery needs the kernel's workers. A token that is issued retires the unused ones before it, so a newer link retires the older ones, and at most `resetRequestsPerHour` (3) links are delivered per credential per hour: a request after that answers as always and delivers nothing. Deliveries that run at the same moment each read the same state before either commits, so each can leave a live link; the links go to the same address, and the hourly cap can be passed by the number of overlapping deliveries. A sign-up of an address that already has a profile answers `auth.identifier_taken`.

Sign-in is for a session: `auth.credential.revoke`, `auth.session.revoke`, `auth.logout`, `auth.reauthenticate`, `auth.extendSession` and `accounts.profile.changePassword` are denied (rules `sessionOnly`, reason "Only a person signed in with a session changes how they sign in.") to every user principal that did not come from this module's session resolver, tested by the kernel-checked `ref.resolver`; an API key, say, reads its owner's credentials and sessions but cannot revoke them, change the password or log out. Operators and module services are not users and are unaffected. `requestPasswordReset`, `resetPassword`, `login` and `signUp` are public, so a rule would gain nothing; a test lists them by name and fails for any other command that admits a user and has no such rule. A rule that exempts a resolver's principals tests `ref.resolver`, never `via` or `claims`.

Configuration: `minPasswordLength` (15; 8 to 64, counted in code points, checked at sign-up, reset and password change, never at login; the longest password is 256 code points), `sessionIdleMinutes` (720), `sessionAbsoluteDays` (30), `reauthenticateWithinMinutes` (10), `successfulLoginsPerMinute` (6), `resetRequestsPerHour` (3) and the three limits above.

Erasing one's own subject is off until the platform switches it on. The module ships no rule for it. The core exports the rule `selfErase` (`import { selfErase } from '@keelwerk/core'`, id `core.eraseSubject.selfErase`), which speaks only of the principal's subject and the input of the core's action: a platform adds it with `policies.add: [selfErase]`; the rule is off whenever it is not in `policies.add`. With it a user may send `core.eraseSubject` for their own subject only, and the session alone is enough: no recent re-authentication is asked, because a rule on a core action cannot ask for one yet. The erasure cannot be undone: the subject's personal values are destroyed in the tenant. In a business tenant the tenant decides what has to be kept, so enable it only where a user may remove their own data. A subject id is never used again after its erasure (the kernel refuses new rows for an erased subject), so a person who comes back signs up again and gets a new subject id.

Not here yet: the profile link of sign-up and the conditional parts for accounts (WP-62), re-authentication, password reset and passkeys.

`src/module.generated.ts` is produced by `pnpm manifests` and the files under `migrations/own/` by the CLI migrations producer; neither is edited by hand.
